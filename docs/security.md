# 威胁模型

v0 的开发档假定：操作者拥有这台机器，控制面进程是可信的，模型输出和未来客户机是不可信的。它防御的是错误授权、提示里的工具滥用、路径逃逸和把开发档误当成生产隔离。它不防御同一用户下的其他进程、root、或者已经能写状态目录的人。

## 已落实的控制

- 所有 API 都要 Bearer 令牌，包括环回地址上的健康检查
- 人类令牌和工作者令牌分开。任务令牌只包含一个项目、一个导出修订和明确的文件列表
- 批准绑定动作、载荷哈希、期望修订和一次性 nonce。过期、重放、字段不一致都失败
- 模型不能通过 `approve: true` 或任务令牌批准自己
- 浏览器 `Origin` 被拒绝，响应不发送 `Access-Control-Allow-Origin`
- `Host` 只能是 `127.0.0.1` 或 `localhost`。配置里的监听地址也只能是环回
- 记忆和导出读取拒绝 `..`、绝对路径、符号链接和 `.git`
- 导出和发布文件带清单哈希，字节变化后读取失败
- 记忆提案在批准前不可被任务读取。没有来源记录的提交对任务令牌返回 `untrusted_source`
- 审计只写角色、动作、结果、修订和哈希。测试检查日志里不出现令牌和合成正文
- 客户机网络参数默认不生成。记忆库、vault 和主目录不能进入共享计划
- 生产剖面和 cloud-hypervisor 后端不会在宿主机上跑任务循环

令牌在首次 `init` 或 `up` 时用 `secrets.token_urlsafe` 生成，写入 `0600` 文件。状态目录是 `0700`。权限变宽后，下一次打开状态会因 `insecure_permissions` 失败。仓库里没有写死的口令。

## 删除做不到彻底擦除

遗忘会从工作树删除文件并写下墓碑，搜索和核心加载不再返回正文。Git 对象和操作者自己的备份里仍然有旧内容。测试用 `git log -p` 确认这一点。

可用的缓解是：不要把口令放进记忆；如果一段内容必须作废，废弃整个仓库和它的备份，而不是只调用 forget。本程序没有加密粉碎，也没有声称运行时内存里的明文受到保护。

## 静态数据

代码实际做的是 Unix 权限和把秘密留在 gitignore 的状态目录里。它没有实现 LUKS、FileVault 或应用层加密。把磁盘加密当作部署前提：macOS 用 FileVault，Ubuntu 用安装时启用的 LUKS。这是操作者在系统里完成的事，不是本仓库已测试的功能。

开发档的失败栈可能把本地路径打到 stderr。HTTP 500 的响应体只有 `internal`，不回显请求正文。

## 明确的缺口

- dev-guard 与模型跑在同一个操作系统用户里。恶意代码如果突破 CPython 进程，就不受工具白名单约束
- 取消是协作式的。mock 会观察取消事件；卡住的本地调用只能等到超时把事件置位。这不是销毁虚拟机
- 没有测量启动时间，也没有可恢复的客户机快照
- 没有 TPM 度量启动，没有把 vault 密封到硬件
- 出站连接器默认不存在。不要把“文档写了拒绝”理解成已经有一个策略防火墙在过滤任意进程
- 审计防不住能直接读状态目录的本机用户

把开发档暴露到局域网，或用同一令牌充当人和工作者，都不在支持范围内。
