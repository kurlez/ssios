# Threat model

The v0 dev profile assumes the operator owns this machine, the control-plane process is trusted, and model output and a future guest are not trusted. It defends against a wrong grant, tool abuse inside a prompt, path escape, and treating the dev profile as production isolation. It does not defend against other processes under the same user, root, or someone who can already write the state directory.

## Controls that are in place

- Every API requires a Bearer token, including the health check on loopback
- The human token and the worker token are separate. A task token contains one project, one export revision, and an explicit file list
- Approval binds the action, payload hash, expected revision, and a one-time nonce. Expiry, replay, and mismatched fields all fail. An expired approval is not renewed. Recovery only opens a new approval bound to the current revision
- The model cannot approve itself with `approve: true` or with a task token. `ssios summary` approves only when standard input contains a single line `yes`. `no`, any other text, and EOF do not approve. Auto-approval in `ssios demo` exists only inside that demo command
- A browser `Origin` is rejected, and the response does not send `Access-Control-Allow-Origin`
- `Host` can only be `127.0.0.1` or `localhost`. The listen address in the config can only be loopback
- Memory and export reads reject `..`, absolute paths, symlinks, and `.git`
- Export and published files carry a manifest hash. A read fails after the bytes change
- A memory proposal cannot be read by a task before approval. A commit with no source record returns `untrusted_source` to a task token
- The audit log writes only the role, action, result, revision, and hashes. Tests check that the log does not contain a token or the synthetic body
- Guest network arguments are not generated by default. The memory repository, the vault, and the home directory cannot enter the share plan
- The production profile and the cloud-hypervisor backend do not run the task loop on the host
- SSIOS's own Git repository uses a separate `HOME` and an empty global config in the subprocess, and it forces signing, external hooks, newline conversion, and external attribute or exclude files off. This does not modify the operator's global Git config

Tokens are generated with `secrets.token_urlsafe` on the first `init` or `up` and written to `0600` files. The state directory is `0700`. After the permissions are widened, the next open fails with `insecure_permissions`. The repository contains no hardcoded password.

## Deletion is not a complete wipe

Forget deletes the file from the worktree and writes a tombstone. Search and core load no longer return the body. The old content remains in Git objects and in the operator's own backups. A test confirms this with `git log -p`.

The available mitigation is: do not put a password in memory. If a piece of content must be retired, retire the whole repository and its backups instead of only calling forget. This program does not cryptographically shred data, and it does not claim that plaintext in runtime memory is protected.

## Data at rest

What the code actually does is Unix permissions and keeping secrets in a gitignored state directory. It does not implement LUKS, FileVault, or application-layer encryption. Treat disk encryption as a deployment prerequisite: FileVault on macOS, and LUKS enabled at install time on Ubuntu. That is something the operator does in the system. It is not a feature this repository has tested.

A failure stack from the dev profile may print a local path to stderr. The HTTP 500 body is only `internal` and does not echo the request body.

## Explicit gaps

- dev-guard and the model run as the same operating-system user. If malicious code breaks out of the CPython process, the tool allowlist does not constrain it
- Cancel is cooperative. The mock observes the cancel event. A stuck local call only sets the event when the timeout arrives. This is not destroying a virtual machine
- There is no measured boot time and no recoverable guest snapshot
- There is no TPM measured boot and no vault sealed to hardware
- There is no outbound connector by default. A document that says "denied" is not a policy firewall filtering arbitrary processes
- The audit log does not stop a local user who can read the state directory directly

Exposing the dev profile to the LAN, or using the same token as both human and worker, is outside the supported range.
